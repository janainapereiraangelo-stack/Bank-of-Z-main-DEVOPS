1 · WASI — Correção #1: Tar de logs vazio em task-wazi-deploy.sh

Problema: O finalize_results executava cd "$outputDir" e depois tentava empacotar um subdiretório logs/ inexistente — o TAR resultante ficava vazio ou falhava silenciosamente. Além disso, o glob wazideploy*.log sem caminho absoluto não achava os arquivos após o cd.

--- .setup/tasks/task-wazi-deploy.sh (antes) finalize_results() { RC=$? mkdir -p "$outputDir" "$evidenceDir" - cd "$outputDir" - if ls wazideploy*.log >/dev/null 2>&1; then - chtag -tc IBM-1047 wazideploy*.log ... - tar cf "$LOG_TAR" "logs" 2>/dev/null || true else echo "No Wazi Deploy logs found" > "$outputDir/wazi-deploy-console.log" - tar cf "$LOG_TAR" "logs" 2>/dev/null || true fi +++ .setup/tasks/task-wazi-deploy.sh (depois) finalize_results() { RC=$? mkdir -p "$outputDir" "$evidenceDir" # sem cd — paths absolutos garantem que o glob e o tar funcionem + if ls "$outputDir"/wazideploy*.log >/dev/null 2>&1; then + chtag -tc IBM-1047 "$outputDir"/wazideploy*.log ... + tar cf "$LOG_TAR" -C "$outputDir" . 2>/dev/null || true else echo "No Wazi Deploy logs found" > "$outputDir/wazi-deploy-console.log" + tar cf "$LOG_TAR" -C "$outputDir" . 2>/dev/null || true fi

2 · WASI — Correção #2: Typo na mensagem de log do generate

Problema: Colchete de fechamento ausente na tag de log — produzia saídas como [GENERATE-BANKZ Applying deployment plan... em vez de [GENERATE-BANKZ] Applying deployment plan....

--- .setup/tasks/task-wazi-deploy.sh (antes) - print_info "[GENERATE-${APP_BASE_NAME} $line" +++ .setup/tasks/task-wazi-deploy.sh (depois) + print_info "[GENERATE-${APP_BASE_NAME}] $line"

3 · TAZ — Correção #3: SCAN_CONFIG_FILE externo sem fallback

Problema: Quando $HOME/zcs_config_file.yml não existia (ambiente novo ou CI), o scan era pulado silenciosamente com exit 0 — sem qualquer análise estática sendo executada, sem erro, sem aviso no log de CI.

Solução em 2 partes: (a) Criado zcodescan/zcodescan-config.yml com a configuração base versionada no repositório. (b) Script atualizado com lógica de fallback explícita.

3a · Arquivo criado: zcodescan/zcodescan-config.yml

+ encoding: IBM-1047 + maxReturnCode: 4 + languages: + - COBOL + - PLI + options: + stopOnError: false + verbose: false + includeCopybooks: true + logging: + level: INFO + file: zcodescan.log

3b · Script atualizado: .setup/tasks/task-zcodescan-static-scan.sh

--- antes - if [ ! -f $SCAN_CONFIG_FILE ]; then - print_warning "ZCodeScan config file not found: $SCAN_CONFIG_FILE. Skipping scan." - exit 0 - fi +++ depois + REPO_SCAN_CONFIG="${SCAN_RULE_FILE%/*}/zcodescan-config.yml" + if [ ! -f "${SCAN_CONFIG_FILE}" ]; then + if [ -f "${REPO_SCAN_CONFIG}" ]; then + print_warning "ZCodeScan environment config not found: ${SCAN_CONFIG_FILE}" + print_warning "Falling back to repository base config: ${REPO_SCAN_CONFIG}" + export SCAN_CONFIG_FILE="${REPO_SCAN_CONFIG}" + else + print_error "ZCodeScan config file not found: ${SCAN_CONFIG_FILE}" + print_error "Repository fallback also missing: ${REPO_SCAN_CONFIG}" + print_error "Create ${SCAN_CONFIG_FILE} or ensure zcodescan/zcodescan-config.yml exists." + exit 1 + fi + fi

4 · GitHub Actions — Correção #4: IP hardcoded em Setup.yml

Problema: bozFrontendUrl: http://9.47.80.84:9081 estava hardcoded, impedindo reuso do workflow em outros ambientes.

--- .github/workflows/Setup.yml (antes) - bozFrontendUrl: http://9.47.80.84:9081 +++ .github/workflows/Setup.yml (depois) + bozFrontendUrl: ${{ vars.BOZ_FRONTEND_URL }}

5 · GitHub Actions — Correção #5: Workflow completo criado (Pipeline.yml)

Problema: A pipeline completa scan → build → deploy → verify existia apenas nos scripts shell, sem nenhum workflow GitHub Actions que a acionasse automaticamente.

Solução: Criado .github/workflows/Pipeline.yml com os seguintes estágios e regras:

JobChamaCondição
controllerImprime parâmetros do runSempre
clonegitClone.sh via SSHSempre
static-scanpipeline-common.sh scanSempre (TAZ)
buildpipeline-common.sh build [tipo]Sempre (DBB)
deploypipeline-common.sh deployApenas push main/release — não em PRs
verifypipeline-common.sh verifyBuild OK + (deploy OK ou deploy pulado)
TriggerBuild typeDeploy?
Push para main ou release/**pipeline (padrão)✅ Sim
Pull Requestpipeline (impacto)❌ Não

6 · DBB — Correção #6: Lifecycle merge documentado

Problema: O lifecycle merge não gerava artefatos de deploy, mas isso não estava documentado no arquivo — equipes podiam confundir sua ausência com um bug.

+++ .setup/build/dbb-build.yaml (adicionado antes do lifecycle merge) + # NOTE: This lifecycle intentionally does NOT include Package, zOSConnect, + # VanillaFrontend, ServerXmlPackager or ImsJavaBuilder. + # It is designed for lightweight validation of topic-branch changes + # before they are merged into the main build branch. + # No deployable TAR artifact is produced by this lifecycle. + # Use the 'pipeline' lifecycle for full CI/CD artifact generation.

Dependências externas e ações manuais necessárias

⚠ Ações que não podem ser automatizadas — requerem configuração manual no GitHub:
  • Criar a variável de repositório BOZ_FRONTEND_URL em Settings → Variables → Actions com o valor correto do ambiente (ex.: http://<seu-host>:9081). Necessária para Setup.yml.
  • As variáveis ZOS_HOST, ZOS_SANDBOX_DIR e o secret GH_ACTIONS_PAT já eram necessários antes — confirmar que estão cadastrados para que o novo Pipeline.yml funcione.
  • O arquivo de configuração ZCodeScan específico por ambiente ($HOME/zcs_config_file.yml no z/OS USS) pode ser criado copiando zcodescan/zcodescan-config.yml do repositório e ajustando parâmetros locais. Sem ele, o fallback do repositório será usado automaticamente.
